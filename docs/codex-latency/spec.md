# Codex 响应速度优化规格

Status: ready-for-human

日期：2026-11-09（Asia/Shanghai）。来源：本轮延迟调查及用户已确认的验收范围。本规格由本地问题跟踪目录发布，此副本随实现分支维护。实施进展见各工单和维护记录。

## Problem Statement

用户在使用公司 Codex 时等待过长，难以判断请求是在重试、等待并发名额、上传历史，还是等待模型输出。公司内链路是 Codex 经局域网访问 NAS Sub2API，再由 Mihomo 海外出口访问 Codex 上游；公司外员工还需经过 SoftEther 双层 VPN。

本轮调查已确认三个不同范围的问题：

- 当前 Codex 声明支持 WebSocket，唯一可调度的 OpenAI OAuth 账号却关闭 WS。握手成功后选号失败，本次会话五次重试才回退 HTTP，约损失 7 秒。当日客户端有 194 次相关重试、39 次回退，服务端对应日志有 310 次 WS 选号失败。
- 另外两个用户的并发限额为 1，共有 25 次名额等待超时，完整请求耗时约 30 秒。当前管理员会话不属于这一组，不能将其归为同一个故障。
- 调查时最近两小时有 6 条请求体超过 64MB 限制的错误记录，返回 413；尚未对应到具体聊天及正文来源。

当前模型及本次会话采用 gpt-6.1-sol / max。当天该模型 max 与 medium 组的单请求处理耗时中位数分别为 31.9 秒和 9.8 秒，但上下文和输出量差异很大，尚不能分离推理强度、会话规模和任务本身的影响。局域网健康接口约 5 毫秒、上游无鉴权网络探测约 1 秒，都不能代替真实模型和公司外 VPN 验收。

## Solution

先让客户端使用当前账号实际支持的 HTTP Responses 流式传输，消除已证实的 WS 失败重试；在保持用户现有入口和模型选择的前提下，以真实 Codex 请求及两端日志建立统一验收记录。随后用隔离会话比较推理强度和长会话整理效果，处置已报 413 的会话，针对两名低并发用户验证适当容量，最后按同一口径对照公司内与公司外 VPN。

用户获得的是更短且可解释的等待、正常的任务与工具执行，以及可追溯的优化结果。无法取得的阶段数据明确留空；未满足条件的场景保留为待验证，不将网络探测成功等同于 Codex 任务完成。

## User Stories

1. 作为公司内的 Codex 用户，我希望新会话直接采用可用协议，以便尽快开始收到回复。
2. 作为经 VPN 接入的员工，我希望使用原有公司入口完成 Codex 任务，以便保留统一接入方式。
3. 作为用户，我希望免去反复失败的连接尝试，以便避免每次新会话额外等待。
4. 作为用户，我希望收到流式输出和正常完成结果，以便确认请求真正执行成功。
5. 作为使用工具的用户，我希望多轮调用保留上下文和工具结果，以便优化传输后仍能完成完整任务。
6. 作为用户，我希望区分首个可见内容与最终完成时间，以便准确描述哪里变慢。
7. 作为维护者，我希望区分客户端到 NAS 与 NAS 到上游的协议，以便修改正确的一段链路。
8. 作为维护者，我希望关联客户端重试与网关请求，以便识别真正失败的阶段。
9. 作为用户，我希望同类任务可以比较 max 和 medium，以便根据质量及等待时间选择推理强度。
10. 作为用户，我希望对照测试尊重现有默认模型和推理选择，以便试验不影响正在进行的工作。
11. 作为维护者，我希望比较任务输入、输出、缓存和失败率，以便避免把不同任务规模造成的差异当作优化效果。
12. 作为长任务用户，我希望通过简短交接延续新会话，以便保留目标、结论和未完成事项。
13. 作为用户，我希望已出现 413 的会话有明确恢复方式，以便停止重复发送超限请求。
14. 作为维护者，我希望在不暴露正文的情况下定位超限会话，以便判断历史、图片或工具输出的影响。
15. 作为用户，我希望取消、断流和超时如实记录，以便失败不会被后续成功掩盖。
16. 作为需要同时处理两项任务的员工，我希望适当的并发名额允许请求进入执行，以便避免无故等待半分钟。
17. 作为维护者，我希望用户名额和上游账号槽位分别计量，以便识别实际容量限制。
18. 作为管理员，我希望只调整已证实受影响的用户，以便容量变更有明确范围。
19. 作为管理员，我希望并发试验保留上游容量余量，以便现有用户能够继续使用服务。
20. 作为远程员工，我希望分别看到 VPN 就绪和 Codex 业务结果，以便连接成功后仍能定位业务故障。
21. 作为维护者，我希望公司内外使用相同任务和统计口径，以便判断 VPN 的实际贡献。
22. 作为维护者，我希望区分独立连接和复用连接，以便避免用连接缓存差异制造改善。
23. 作为维护者，我希望保留所有失败样本和重试时间，以便性能统计反映实际体验。
24. 作为维护者，我希望按实际运行版本核对配置，以便旧镜像标签不会导致错误升级判断。
25. 作为管理员，我希望每次配置调整都有备份和回滚证据，以便异常时恢复服务。
26. 作为员工，我希望诊断只保存必要的脱敏元数据，以便个人正文、凭据和身份资料受到保护。
27. 作为项目负责人，我希望每项工单都有独立验收结果，以便分清已修复、待验证与无收益的方案。
28. 作为项目负责人，我希望交付包含实测收益和适用条件，以便决定是否扩大部署或继续调整网络。

## Implementation Decisions

- **先修配置，再评估其他收益。** 首个候选仅关闭当前 Codex provider 的 WS 能力声明，使新会话直接使用 HTTP Responses 流式传输。保留现有入口、认证、模型和员工 VPN 配置，不同时调整其他变量。
- **明确两段传输。** 客户端到 NAS 的 WS 入口要求可兼容的账号模式。当前账号为 off，单独更改 NAS 到上游的 force_http 开关不能代替客户端能力对齐。本规格采用当前可用的 HTTP 路径，不引入 WS bridge 或上游协议迁移。
- **依托一个主要验收边界。** 在已安装 Codex 的正常请求及流事件边界采样，并关联两端日志；现有 HTTPS 对照工具只辅助解释网络阶段。复用调查中的日志、用量汇总和网络分段能力，确有缺口时只补一个统一采集与汇总适配层。
- **统一计时语义。** 客户端全程耗时从提交测试任务到该任务完成或终止；首可见输出为首个实际用户可见内容事件。网关首语义事件、单次转发耗时、用户名额等待、账号槽位等待和工具执行分别记录，不能直接相加或相互替代。使用各自进程的单调时钟计算阶段时长，跨主机只通过关联标识和已校对时间线分析。
- **保留失败与重试。** 每个测试任务记录原始尝试数、回退、状态、可用计时和最终结果。断流、取消、413、并发超时均进入分母；失败不能通过丢弃样本或只报告最后一次成功隐藏。
- **推理对照保持隔离。** 固定同一已安装运行版本、模型、任务、工具和出口，仅在隔离测试配置中比较 max 与 medium。现有默认值保持用户选择；以数据产出推荐，不预设全局降档或固定加速倍数。
- **长会话优先交接。** 交接保留当前目标、已确认结论、必要证据位置、有效约束和下一步；不搬运全量历史或敏感正文。对已报 413 的会话先定位再恢复，不通过一味扩大正文限制维持超大请求。
- **并发分层、限定对象。** 已定位的两名用户为首批评估对象，当前限额为 1。先在受控用户复现单名额竞争，再验证两路需求；若容量及对照通过，可将 2 作为这两名用户的分阶段试点候选。上游账号现有 20 槽位及管理员现有设置不自动改动，最终值须由实际负载结果支持。
- **远程验证独立。** 公司内和公司外 VPN 结果分别统计。沿用现有双层隧道、证书固定及精确 VPN 入口 DIRECT 规则，使用专用测试会话；不抢占员工连接或清空共享 DNS/Fake-IP 缓存。
- **变更可恢复。** 记录有效配置与真实运行版本，备份保留于受控管理位置。小范围应用候选后核对健康、完成率和行为；出现新增认证、上下文或流式完成异常时恢复原值并记录结果。
- **交付维持既有接口。** 本规格不新增员工业务接口、不改数据库结构；诊断沿用现有脱敏约定，只保存计时、状态、计数、版本和关联所需元数据。

## Testing Decisions

用户已确认：以“真实 Codex→NAS→上游请求及两端日志”为主验收接缝，检查首可见输出、完成时间、重试和失败；HTTPS 探测仅用于辅助定位网络。

测试只断言外部可观察结果和真实失败模式，不绑定内部函数调用顺序、日志源码行号或私有实现。优先复用现有 Windows HTTPS 对照、客户端诊断、调查中的本机日志提取、网关只读统计及访问日志关联；不为一行可恢复配置调整另建镜像实现的单元测试。仅当统一采集层新增解析与统计逻辑时，才用脱敏记录验证丢事件、取消、重试、缺失计时和失败分母。

执行前固定以下口径，并随结果保存：

- **任务与质量。** effort 筛查包含固定格式短回答、读取临时文本后计算可核对结果、至少三轮工具结果引用三类任务；先冻结输入、预期值和必须满足的检查点，两档使用相同夹具。分别报告每类任务的配对差值，正确性检查全部通过才讨论该类的速度取舍；出现质量退化或方向不一致时不作统一档位建议。五对筛查只支持本轮描述性结论，不据此切换全局默认。会话交接首先验收目标恢复；只有取得相同目标在原会话与交接新会话的可比基线，才报告速度收益。
- **关键采样。** 每条记录至少包含测试任务标识、会话及请求/尝试关联、网络位置、版本、模型和 effort、提交及结束事件、结束状态、重试数、缺失字段及原因。首可见事件缺失时，该指标未验收；缺少协议证据或两路进入上游的证据时，对应行为不得通过。DNS、单侧阶段或跨主机计时缺失可保留为空，不阻止已有充分证据的其他项目验收。
- **并发试点。** 受控验证与真实用户试点分别记状态。生产试点前记录至少 5 分钟现有负载，并确认能为两路需求保留至少 4 个上游槽位余量；不能取得可靠槽位数据时停留在受控评估。先用户 5、后用户 2，每次只变更一个用户，观察至少 30 分钟且取得至少 3 组两路需求结果后再决定是否保留及继续。出现账号等待超时、新增上游限流、认证或流式完成异常时恢复该用户原值；已有运行请求正常结束，不主动中断其他会话。无代表性并发请求时，记录业务效果未验收。
- **VPN 复测。** 优先同设备、同账号在 15 分钟内交错比较公司 Wi-Fi 与外部网络经 VPN；跨设备或跨较长时段时，标记可比性限制。VPN 侧独有失败、至少三对出现同一接入阶段变慢，或任务差异无法由上下文和上游解释时进入针对性复测。筛查只形成描述性发现；只有重复问题已定位到具体网络阶段并具备可恢复候选时，才提出网络变更，不能仅凭一次配对差异改网。

| 场景 | 验收行为与方法 |
| --- | --- |
| WS 配置对齐 | 至少 5 个独立新会话完成固定短任务；测试相关日志直接采用 HTTP，无 WS 选号失败、五次重试或协议回退；保留现有任务文本结果及正常结束事件。历史已复现时间线作为修复前依据，不为复现故意破坏共享配置。 |
| 多轮与工具 | 固定一项至少三轮、包含工具调用及结果引用的任务，核对后续轮次保留上下文且完整结束；测试只读临时夹具，不改业务文件。该任务属于同一端到端验收边界。 |
| effort 与会话规模 | 先用至少 5 对同任务交错对照筛查，每组明确预热、上下文、缓存、输入/输出和质量判据；只比较任务正确完成的同类条件，同时报告所有失败。样本不足时只给描述统计，不给稳定 P95 或倍数承诺；有价值且仍不确定时才扩大采样。 |
| 413 恢复 | 先用现有失败记录及只读关联定位受影响会话；交接后的新会话能完成同一未完成目标且不再返回 413。超限边界的重放限于脱敏记录或隔离环境，不向生产发送超大正文；定位不到时明确保留归属缺口。 |
| 并发名额 | 受控用户在限额 1 时发送两路重叠任务，确认第二路等待发生在用户名额；候选限额 2 时两路都能进入上游且正常完成，不再出现同类约 30 秒用户名额超时。每种状态至少 3 组，用关联日志区分上游拥塞，不以同时发出请求证明同时执行。 |
| 公司外 VPN | 在可用的公司外测试设备上保持任务、版本、账号、effort 和出口一致，分别记录 VPN 就绪、到 NAS、上游等待及客户端全程结果；没有对应实机数据时标记未验收。网络性能结论沿用每目标至少 20 次独立连接和 20 次复用连接的既有取样约定。 |
| 回滚与隐私 | 核对仅目标配置变化，恢复后原认证、入口、模型及正常任务可用；交付中不含凭据、完整请求正文、账号身份或原始敏感配置。 |

不同阶段和不同网络分别统计成功率、首可见输出、完成时间及失败类别。跨主机阶段缺失时留空并给原因，不能用网关 semantic 指标或健康接口 200 冒充用户首字及业务完成。修复的最小成功标准是已证实的协议失败过程消失且任务行为通过；其余优化按各自对照结果验收，不能互相代替。

## Out of Scope

- 本次规格发布期间执行客户端配置、用户并发、模型默认值或生产服务变更。
- 改写 Sub2API 账号调度器、增加新的中转层、数据库迁移，或直接启用 WS bridge。
- 因旧镜像标签直接升级服务，或在没有同任务证据时采购新 NAS、VPN、代理或上游账号。
- 全公司统一提高并发、全局自动降低推理强度、无界扩张模型对照负载。
- 扩大请求体限制、自动删除或压缩用户原始聊天、复制全量敏感历史。
- 修改 VPN 证书验证、清空共享 DNS/Fake-IP 缓存、扩大 DIRECT 规则或中断员工当前连接。
- 恢复此前已暂缓的同事飞书故障调查，或用网站探测替代其业务验收。

## Further Notes

术语：Sub2API“用户”是请求使用者及其并发名额；“上游账号”是被网关选中的 OAuth/API Key 身份及账号槽位；“模型请求”是一段转发，“Codex 任务”可包含多个请求与工具调用。“WS”必须明确客户端→NAS 或 NAS→上游。

本轮运行接口返回 Sub2API 0.2.20，容器旧镜像标签为 0.2.15 且存在更新运行目录；后续实施先核对真实运行版本。当前首 token 统计未设置独立覆盖值，对应版本默认 semantic，可能早于可见文字；网关转发计时排除前置排队、上传和此前 WS 重试。

社区原发案例用于选择实验，现场结论以当前配置、日志及对照结果为准。原调查及历史验证保持原文，实施采用本目录的新规格和独立工单。
