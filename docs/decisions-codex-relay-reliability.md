# Codex 中转可靠性方案

2026-11-17。大陆办公室和远程员工；现有 NAS Docker、Sub2API、Postgres、Redis 和海外代理具备维护入口。保留团队共享入口与用户管理。凭据和原始请求仅在受控本机/NAS，不进公开仓库。预置备用账号现已完成真实推理和费用记账验收，用户明确批准限额启用；金额保留在受控记录。

### 方案 A：现有 Sub2API 配置加固
- 技术栈：既有 Go 网关、Postgres、Redis 和代理，使用原生协议与超时配置。
- 为什么适合：直接覆盖已观察到的 HTTP/2 断流和无界等待。
- 开发难度 / 维护成本：低至中，无新增长期组件。
- 目标地区能否顺利使用：沿用已实测公司接入和海外出口，持续验证实际业务。
- 你得自己管的东西：现有密钥、数据库权限、NAS 补丁、配置备份及回退。
- 主要风险：超时过短会截断合法高推理任务；不能消除上游容量不足。

### 方案 B：现有中转增加已验收备用上游
- 技术栈：现有网关的账号/代理调度与独立备用账号或出口。
- 为什么适合：故障时切换到实际有容量的独立资源。
- 开发难度 / 维护成本：中，需要授权、额度监控及切换验收。
- 目标地区能否顺利使用：本轮已通过公司现有出口实测；后续新增服务仍需分别核对支持地区和实际链路。
- 你得自己管的东西：新增密钥、费用、权限、有效期及两条链路测试。
- 主要风险：共用拥塞来源不能提供独立容错；未就绪账号不能直接启用。

### 方案 C：员工官方 Codex 账号直连
- 技术栈：官方客户端、员工独立账号和公司海外网络。
- 为什么适合：减少自建中转维护环节。
- 开发难度 / 维护成本：迁移和逐人授权管理成本较高。
- 目标地区能否顺利使用：需核对官方地区政策及网络，不假定新增直连可用。
- 你得自己管的东西：员工账号、权限、费用及本地出口。
- 主要风险：改变共享入口、用量管理和员工流程；仍可能遭遇上游过载。

初始推荐：方案 A，已有程序提供对应配置，可先修复故障处理。

最终推荐与用户选择：方案 A + B。用户在备用账号完成真实验证后，明确选择按 24 小时额度阈值启用，并发 1；金额仅存受控记录。决定因素是预置资源已可用，能在主账号不可用时继续服务。配置使用原生订阅优先和会话重新评估，已验证恢复回切与额度耗尽停用。未采购新服务、未迁移 C。

仍会改变本轮实施的待定问题：无。长期稳定和外部容量仍需实际观察。
