# Feature Specification: 009-codex-relay

## User Scenarios & Testing
用户于 2026-11-17 明确要求修复现有 Codex 中转高延迟，并指定 architect 比较方案。大陆办公室和远程员工继续使用已有 NAS 中转及海外出口。配置变更由维护者完成；未要求新增采购或改变模型选择。

正常流式请求应完整完成；上游协议不稳定时采用 HTTP/1.1；上游不响应或只保活不产生输出时应在配置预算内退出。故障注入使用独立数据库、Redis、账号及本地上游。

## Requirements
- **FR-001**: OpenAI 上游使用原生 HTTP/1.1 配置，在隔离真实程序验证协议和完整流结束。
- **FR-002**: 响应头、首语义输出和流数据间隔有界等待；高推理保留更长预算，以无响应/保活/停流注入验证。
- **FR-003**: 核验过载时有限重试、取消及错误结束，不把 HTTP 200 当作流成功，不声称本地配置消除上游容量不足。
- **FR-004**: 持久化前备份，提供冲突检查回退，保留用户/账号/密钥与原交付；生产真实请求完整完成。
- **FR-005**: 保存方案比较、生产验证和剩余边界，更新运维入口；公开仓库仅保留脱敏说明。
- **FR-006**: 按用户批准的预算阈值启用现有备用账号，并发为 1；验证订阅优先、过载切换、同会话回切、额度耗尽停用和实际费用记账。

## Success Criteria
隔离真实程序完成协议与故障行为验证；生产小请求、多路请求均有完整结束事件；短时观察无新增 HTTP/2 错误。保存配置、程序哈希、命令和通过数；不承诺固定推理耗时或长期稳定。

## Clarifications
既有授权涵盖修复及必要重启；不代签人工评审。后续核验发现预置 API 账号可用，用户明确选择限额启用；本轮最终实施现有服务加固与限额备用。预算金额和原始证据保留于受控运维记录。
